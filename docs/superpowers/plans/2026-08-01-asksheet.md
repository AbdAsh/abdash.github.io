# AskSheet Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Drop a CSV, ask questions in English, get answers with visible SQL and charts — with the data never leaving the browser. Deployed at `labs.abdash.net/asksheet`.

**Architecture:** DuckDB-WASM runs in a worker and holds the data locally. The only server call sends a *schema profile* plus the question to `asksheet-plan`, which returns strict JSON containing SQL and an optional Vega-Lite spec. The client executes that SQL against its local table. One automatic repair round-trip on SQL error.

**Tech Stack:** Vite 8 · React 19 · TypeScript 6 · `@duckdb/duckdb-wasm` · PapaParse · `vega-lite` + `vega-embed` · `@labs/platform`.

## Global Constraints

- **Prerequisite: the platform plan is complete.**
- **Row data must never leave the browser.** This is the product thesis and a hard invariant — the only outbound payload is column names, inferred types, row count, and at most five sample values per column (zero in strict mode).
- AskSheet owns **no Postgres schema and no storage**. It touches only `platform.usage_counters` via `consume_quota`.
- Planner uses OpenRouter `MODEL_CHEAP`. No embeddings.
- Vite `base: '/asksheet/'`.
- Ship the **single-threaded** DuckDB bundle first; cross-origin isolation only if measurement demands it.

- [ ] **Step 1: Scaffold the app**

`vite.config.ts` sets `base: '/asksheet/'`, plugin-react, and `optimizeDeps: { exclude: ['@duckdb/duckdb-wasm'] }`.

- [ ] **Step 2: Bootstrap DuckDB with the single-threaded bundle**

```ts
import * as duckdb from '@duckdb/duckdb-wasm'

let db: duckdb.AsyncDuckDB | null = null

/** Selects the MVP (single-threaded) bundle deliberately: the EH/threaded bundle
 *  needs SharedArrayBuffer, which needs COOP/COEP headers on this path. We start
 *  without that constraint and only add it if profiling shows we need it. */
export async function initDuck(): Promise<void> {
  if (db) return
  const bundles = duckdb.getJsDelivrBundles()
  const bundle = await duckdb.selectBundle(bundles)
  const worker = new Worker(bundle.mainWorker!, { type: 'module' })
  db = new duckdb.AsyncDuckDB(new duckdb.ConsoleLogger(duckdb.LogLevel.WARNING), worker)
  await db.instantiate(bundle.mainModule, bundle.pthreadWorker)
}
```

- [ ] **Step 3: Register a CSV and read back its schema**

```ts
export async function registerCsv(file: File | string, tableName = 'data'): Promise<ColumnInfo[]> {
  await initDuck()
  const conn = await db!.connect()
  try {
    if (typeof file === 'string') {
      await db!.registerFileText(`${tableName}.csv`, file)
    } else {
      await db!.registerFileBuffer(`${tableName}.csv`, new Uint8Array(await file.arrayBuffer()))
    }
    await conn.query(`create or replace table ${tableName} as
                      select * from read_csv_auto('${tableName}.csv', SAMPLE_SIZE=-1)`)
    const described = await conn.query(`describe ${tableName}`)
    return described.toArray().map((r: never) => ({
      name: String(r.column_name), type: String(r.column_type),
    }))
  } finally {
    await conn.close()
  }
}
```

- [ ] **Step 4: Implement `runQuery` with a timeout and row cap**

Wrap the query in `Promise.race` against a timer (default 10 s) and `LIMIT`-guard the result at 5,000 rows for display, so a pathological cross join cannot freeze the tab. Return elapsed milliseconds — it feeds the responsiveness success criterion.

- [ ] **Step 5: Write an integration test against a bundled sample**

`duck.test.ts` registers a small inline CSV string and asserts: schema inference returns expected types, a `select count(*)` returns the right number, and a deliberately slow query rejects with a timeout error.

- [ ] **Step 6: Run, then commit**

## Task 2: Schema profiling and the privacy boundary

**Files:**
- Create: `apps/asksheet/src/lib/profile.ts`, `profile.test.ts`

**Interfaces:**
- Produces:
  ```ts
  export interface Profile {
    table: string
    columns: { name: string; type: string; samples: string[] }[]
    rowCount: number
  }
  export async function buildProfile(table: string, strict: boolean): Promise<Profile>
  ```

**This task is the privacy contract in code.** Everything the server ever sees is produced here and nowhere else.

- [ ] **Step 1: Write the failing test — this is the important one**

```ts
import { describe, it, expect } from 'vitest'
import { redactProfile } from './profile'

const raw = {
  table: 'data',
  rowCount: 5000,
  columns: [
    { name: 'email', type: 'VARCHAR', samples: ['a@b.c', 'd@e.f', 'g@h.i', 'j@k.l', 'm@n.o', 'p@q.r'] },
    { name: 'amount', type: 'DOUBLE', samples: ['1', '2', '3'] },
  ],
}

describe('redactProfile', () => {
  it('caps samples at five per column in normal mode', () => {
    const p = redactProfile(raw, false)
    expect(p.columns[0]!.samples).toHaveLength(5)
  })

  it('removes every sample value in strict mode', () => {
    const p = redactProfile(raw, true)
    expect(p.columns.every((c) => c.samples.length === 0)).toBe(true)
  })

  it('preserves column names, types and row count in strict mode', () => {
    const p = redactProfile(raw, true)
    expect(p.columns.map((c) => c.name)).toEqual(['email', 'amount'])
    expect(p.rowCount).toBe(5000)
  })

  it('never emits a key other than table, rowCount and columns', () => {
    const p = redactProfile({ ...raw, secretRows: [[1, 2]] } as never, false)
    expect(Object.keys(p).sort()).toEqual(['columns', 'rowCount', 'table'])
  })
})
```

The last case guards against a future refactor accidentally widening the payload — it asserts the shape by exclusion, not by inclusion.

- [ ] **Step 2: Run, confirm failure, implement `redactProfile` and `buildProfile`**

`buildProfile` queries `select count(*)` and, unless strict, `select distinct <col> ... limit 5` per column, then passes the result through `redactProfile`. Only the redacted object is ever returned.

- [ ] **Step 3: Run tests, then commit**

## Task 3: SQL validation guard

**Files:**
- Create: `apps/asksheet/src/lib/validate.ts`, `validate.test.ts`

**Interfaces:**
- Produces: `export function assertSingleSelect(sql: string): void` — throws `UnsafeSqlError` otherwise.

- [ ] **Step 1: Write the failing tests**

```ts
const bad = [
  'PRAGMA database_list',
  'COPY data TO \'/tmp/x.csv\'',
  'ATTACH \'x.db\' AS y',
  'select 1; drop table data',
  'INSTALL httpfs',
  'delete from data',
]
const good = [
  'select * from data',
  'SELECT a, b FROM data WHERE x > 1 ORDER BY a',
  'with t as (select 1 as n) select n from t',
  'select * from data;',                    // single trailing semicolon is fine
]
```

Assert every `bad` throws and every `good` passes. The CTE case matters — a naive "must start with select" check would reject legitimate `WITH` queries the planner will produce.

- [ ] **Step 2: Implement**

Strip comments and string literals first, then: reject if more than one statement remains after dropping a single trailing semicolon; reject any of `pragma|copy|attach|install|load|insert|update|delete|drop|create|alter|export`; require the first keyword to be `select` or `with`.

const SCHEMA = {
  type: 'object',
  additionalProperties: false,
  required: ['sql', 'narration'],
  properties: {
    sql: { type: 'string', description: 'A single DuckDB SELECT statement.' },
    narration: { type: 'string', description: 'One sentence framing the answer.' },
    chart: {

  },
} as const

The system prompt states the DuckDB dialect, the exact table name and schema, the single-SELECT rule, and that prior question→SQL pairs are context — never results, because results are data.

Guard the request body size (reject over 32 KB) so an oversized "profile" cannot be used to smuggle rows.
